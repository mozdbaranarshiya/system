# انتقال سامانه به پروژهٔ Supabase مشترک

مقصد انتخاب‌شده `pukanizbahswrupscfmg` است. این پروژه از قبل `exam-api` و جدول‌های آزمون در `public` دارد. مالک شروع مدرسهٔ تازه در مقصد، بدون انتقال کاربران و داده‌های قبلی را انتخاب کرده است. سایت فعلی هنوز به `efibfevyiepkwpnobaro` متصل است؛ آماده‌شدن مدیر واقعی و پذیرش مقصد، پیش‌نیاز تغییر اتصال سایت هستند. پروژه و داده‌های مبدا در این مسیر حذف نمی‌شوند.

## معماری مقصد

جدول‌ها، نوع‌ها، Permissionها و RPCهای مدرسه در `school` نصب می‌شوند. `school_private` و `school_oauth` خصوصی و خارج از فهرست schemaهای Data API هستند. فایل‌های تکلیف در Bucket خصوصی `school-assignment-files` قرار می‌گیرند. جدول‌های `public`، تابع `exam-api`، کاربران موجود و تنظیمات Auth سرویس آزمون حفظ می‌شوند.

Auth و MFA همچنان Supabase بومی‌اند و بین برنامه‌ها مشترک هستند. مدیر مدرسه فقط کاربران دارای پروفایل همان مدرسه را مدیریت می‌کند. حذف دسترسی مدرسه، حساب Auth مشترک و تاریخچه را حفظ می‌کند و اتصال‌های OAuth مدرسه را لغو می‌کند. تغییر ایمیل یا رمز یک هویت مشترک بر همهٔ برنامه‌های استفاده‌کننده از همان هویت اثر دارد؛ انتقال نباید کاربران نامرتبط مقصد را با کاربران مدرسه تطبیق دهد.

در `admin-user` و تغییر رمز مدیر، معتبرشدن JWT از Auth به‌تنهایی کافی نیست. RPC فقط-service `school.assert_manager_session` باید فعال‌بودن مدیر و هویت Auth، Session جاری AAL2 و عامل TOTP تأییدشدهٔ همان Session را تأیید کند. حذف عامل یا Session، انقضا یا downgrade و خطای بررسی باعث رد عملیات می‌شود. تغییر رمز اولیهٔ خود مدیر پس از MFA معتبر ممکن است؛ سایر عملیات مدیریت حساب آماده می‌خواهند. اتصال و مدیریت OAuth علاوه بر این کنترل‌ها TOTP تازه در ۱۰ دقیقهٔ گذشته می‌خواهد.

## وضعیت بررسی‌شدهٔ مقصد — ۲۰۲۶-۱۰-۰۹

ساختار مستقل روی مقصد نصب شده است: ۴۷ جدول `school` و ۷ جدول خصوصی `school_oauth` همگی RLS دارند و تعداد پروفایل مدرسه صفر است. شمارش رکوردهای شش جدول آزمون قبلی، کاربران Auth موجود، تعریف ستون‌ها، Policyها و تابع‌های `public`، Triggerهای قبلی Auth و Bucketهای قبلی با snapshot پیش از نصب برابر بودند. نصب، FK و Triggerهای مجزای مربوط به خود مدرسه را اضافه می‌کند.

هر سه تابع `oauth-connector`، `admin-user` و `account-security` در نسخهٔ ۲ با وضعیت `ACTIVE` و `verify_jwt=false` مستقر هستند؛ تابع موجود `exam-api` در بررسی پایانی نسخهٔ ۷ و فعال است. تنظیمات سفارشی `SYSTEM_DB_SCHEMA=school` و `OAUTH_*` اعمال شده‌اند و Data API فقط schemaهای `public,graphql_public,school` را expose می‌کند. `pg_cron` نسخهٔ ۱.۶.۴ و دو Job فعال مستقل برقرارند: یادآوری با `*/15 * * * *` و cleanup با `17 * * * *`.

دامنهٔ مقصد اکنون از محیط قابل‌دسترسی است و ۲۱ بررسی مستقیم HTTP سرویس مستقر موفق بودند: رد درخواست ناقص/Client ثبت‌نشده و توکن نامعتبر، حفاظت API و مسیرهای حساب/مدیریت، Origin و CORS دقیق و Headerهای امنیتی، عدم expose شدن schema خصوصی و عدم دسترسی `anon` به RPC اثبات MFA مدیر. این بررسی‌ها مرزهای درخواست نامعتبر و تنظیمات runtime/RPC را آزمودند؛ آزمون ورود و چرخهٔ کامل کاربر نبودند.

طبق انتخاب مالک، کاربران، داده‌ها و فایل‌های مدرسهٔ مبدا منتقل نمی‌شوند. `config.js` این شاخه برای مقصد آماده است؛ سایت منتشرشده هنوز به مبدا متصل است و تغییر آن به آماده‌شدن مدیر نخست وابسته است. مدیر واقعی مدرسهٔ تازه و Client واقعی ChatGPT هنوز آماده نشده‌اند؛ نتیجهٔ نصب و استقرار، تأیید ورود کاربر یا اتصال واقعی ChatGPT نیست. مراحل مالک و راهنمای فعال‌سازی در [CHATGPT_SETUP.md](CHATGPT_SETUP.md) آمده‌اند.

## نصب مقصد

```bash
npm run test:schema
node supabase/install-school.mjs --out /tmp/system-school-reviewed-install
```

ابزار به دیتابیس متصل نمی‌شود. SHA-256 هفت فایل منبع، شامل schema پایه، چهار Migration نسخهٔ ۷، OAuth و کنترل Session مدیر را بررسی و هشت مرحلهٔ SQL مقصد و Manifest تولید می‌کند. فایل‌های اصلی نصب `public` تغییر نمی‌کنند. `install.sql` تمام مرحله‌ها را در یک تراکنش اجرا می‌کند و با وجود schema، Bucket، Policy، Trigger یا Job همنام متوقف می‌شود؛ اجرای دوباره روش ارتقا نیست. مقصد انتخاب‌شده اکنون نصب شده است؛ این دستور برای تولید و بازبینی artifact است و SQL آن نباید دوباره روی این مقصد اجرا شود.

پس از بررسی catalog مقصد و Manifest، فقط `install.sql` تولیدشده را با نقش مالک دیتابیس روی مقصد انتخاب‌شده اجرا کنید. فایل‌های اصلی `schema.sql` و Migrationها را مستقیم روی `public` این پروژه اجرا نکنید. پس از نصب، فهرست schemaهای Data API قبلی را حفظ و فقط `school` را اضافه کنید؛ schemaهای خصوصی را expose نکنید.

متغیرهای سفارشی Edge Functionها:

```text
SYSTEM_DB_SCHEMA=school
OAUTH_SITE_URL=https://mozdbaranarshiya.github.io/system/index.html
OAUTH_ALLOWED_ORIGINS=https://mozdbaranarshiya.github.io
OAUTH_ALLOW_LOCAL_HTTP=false
```

کلیدهای `SUPABASE_*` سرور را runtime فراهم می‌کند. کلید Service Role یا Secret را در مخزن، مرورگر یا ChatGPT قرار ندهید. `admin-user`، `account-security` و `oauth-connector` را جداگانه با `--project-ref pukanizbahswrupscfmg --no-verify-jwt` مستقر کنید؛ `exam-api` را prune یا جایگزین نکنید. `verify_jwt=false` برای هر سه تابع در `supabase/config.toml` ثبت شده است. هر تابع JWT دقیق کاربر را از Supabase Auth معتبر می‌کند و نقش و Session را سمت سرور کنترل می‌کند؛ OAuth توکن opaque را نیز مستقل بررسی می‌کند. این تنظیم از کلید Publishable جدید پشتیبانی می‌کند.

مقصد از امضای فعال `ES256` و کلیدهای API جدید استفاده می‌کند. کلیدهای قدیمی `anon`/`service_role` در مقصد غیرفعال و کلید امضای قبلی `HS256` لغو شده‌اند؛ پیکربندی جدید باید Publishable/Secret Key باشد. تابع‌ها ابتدا `SUPABASE_PUBLISHABLE_KEYS` و `SUPABASE_SECRET_KEYS` مورداعتماد runtime را می‌خوانند. تطبیق Hash تنظیم سرویس آزمون با Publishable Key مقصد پیش از تغییر تأیید شد؛ هیچ Secret یا کلید سمت سرور در مستندات یا مخزن ثبت نمی‌شود. این تغییر فقط مقصد را شامل می‌شود و کلیدهای پروژهٔ مبدا را تغییر نمی‌دهد.

پس از لغو کلید قدیمی، همان ۲۱ بررسی مدرسه دوباره موفق شدند. درخواست خواندن سرویس آزمون با توکن ساختگی، پاسخ `401` موردانتظار دیتابیس را برگرداند و مسیر Edge→REST آن بررسی شد؛ سایت آزمون و فایل تنظیم عمومی آن نیز HTTPS `200` داشتند. این آزمون‌ها از توکن یا اطلاعات واقعی کاربر استفاده نکردند.

پیش از تغییر اتصال سایت، تنظیم عمومی آمادهٔ مقصد باید شامل URL پروژه، **فقط Publishable Key**، `SUPABASE_DB_SCHEMA: "school"`، `ASSIGNMENT_BUCKET: "school-assignment-files"` و `SUPABASE_AUTH_STORAGE_KEY: "system-school-pukan-auth"` باشد. Cache مرورگر براساس پروژه، schema و UUID جداست و Session پروژهٔ قبلی برای مقصد استفاده نمی‌شود.

صفحه‌های `/exam/` و `/system/` در GitHub Pages یک Origin و در مقصد یک پروژهٔ Auth دارند. کلید ثابت و مستقل `SUPABASE_AUTH_STORAGE_KEY`، ذخیره و هماهنگی Session مدرسه را از کلید پیش‌فرض SDK برنامهٔ آزمون جدا می‌کند. اگر این تنظیم نباشد، کلید پیش‌فرض نصب قبلی حفظ می‌شود. خروج عادی، رد دسترسی مدرسه و لغو/خطای MFA در schema مستقل با `scope: "local"` فقط Session جاری مدرسه را خارج می‌کنند. دکمهٔ صریح «خروج از همه دستگاه‌ها» همچنان `scope: "global"` دارد و Sessionهای همان هویت مشترک را در برنامه‌های دیگر نیز لغو می‌کند. رمز و عوامل MFA همچنان به هویت بومی مشترک تعلق دارند.

اگر `pg_cron` هنگام نصب موجود باشد، دو Job مستقل `school-v7-reminders` و `school-oauth-cleanup` ساخته می‌شوند. در غیر این صورت مالک دیتابیس باید افزونه و همین Jobها یا scheduler مورداعتماد دیگری را برقرار کند. دستورهای زمان‌بندی، `select school.generate_school_reminders();` هر ۱۵ دقیقه و `select school.oauth_cleanup();` هر ساعت هستند. Jobهای برنامهٔ قبلی حفظ شوند؛ namespace `public` در این دستورها مقصد مدرسه نیست. انقضای توکن در هر درخواست بررسی می‌شود و به اجرای cleanup وابسته نیست.

## راه‌اندازی مدرسهٔ تازه

مدیر واقعی در Auth مقصد با ایمیل `کدملی@school.local` و رمز قوی ساخته شود و پروفایل `school.profiles` به UUID همان حساب متصل شود. اطلاعات حساب واقعی را از مالک دریافت کنید؛ حساب موجود سرویس آزمون را به‌طور خودکار مدیر مدرسه نکنید و مدیر نمایشی نسازید. مدیر در سایت خود Enrollment بومی TOTP و تغییر رمز اولیه را تکمیل می‌کند؛ بدون MFA معتبر کد OAuth صادر نمی‌شود. رمز یا JWT مدیر برای ثبت Client ChatGPT در چت یا ابزار توسعه ارسال نشود.

## انتقال اختیاری داده‌های قبلی

این بخش برای تصمیم احتمالی بعدی به انتقال داده‌های قبلی است و جزو راه‌اندازی تازهٔ انتخاب‌شده نیست. دسترسی مدیریت، SQL فقط‌خواندنی و فهرست تابع‌های مبدا با توکن جداگانهٔ `SUPABASE_SOURCE_ACCESS_TOKEN` تأیید شده است. توکن `SUPABASE_ACCESS_TOKEN` همچنان مخصوص مقصد است. بررسی فقط‌خواندنی، کاربران و داده‌های واقعی مدرسه و تابع‌های زندهٔ `chatgpt-api`، `chatgpt-mcp` و `consent-location` را در مبدا نشان داد؛ وجود آنها به‌تنهایی تأیید امنیت یا اتصال عملی ChatGPT نیست. قبل از هر استقرار روی مبدا، پیاده‌سازی فعلی باید بررسی و حفظ شود. برقراری دسترسی، انتخاب شروع تازه را تغییر نمی‌دهد و مجوز انتقال یا حذف داده‌ها نیست. انتقال به دسترسی مجاز مالک مبدا یا Backup رسمی شامل schemaهای مدرسه و Auth نیاز دارد؛ کلید عمومی سایت جایگزین آن نیست.

1. نوشتن داده در مبدا را برای مرحلهٔ نهایی کنترل و Backup قابل‌بازیابی تهیه کنید.
2. UUIDهای `auth.users`، Hash رمز، `auth.identities` و تمام FKهای پروفایل/کلاس/نمره حفظ شوند. ایجاد مجدد کاربران از Excel یا صرفاً تطبیق ایمیل، انتقال معتبر نیست.
3. هر تعارض UUID یا ایمیل با کاربران موجود مقصد باید پیش از import حل شود؛ حساب موجود سرویس آزمون را overwrite یا به‌طور خودکار به مدرسه متصل نکنید.
4. داده‌های مدرسه از namespace مبدا به `school` منتقل و FKها، شمارش رکوردها و دسترسی واقعی نقش‌ها مقایسه شوند. DDL قدیمی Backup را روی `public` مقصد اجرا نکنید.
5. محتوای فایل‌های Storage جداگانه منتقل شود؛ Backup دیتابیس فقط metadata فایل‌ها را دارد. مسیر UUIDها، خصوصی‌بودن Bucket و مجوزها پس از انتقال بررسی شوند.
6. Session، JWT، Refresh Token و Grantهای OAuth پروژهٔ قبلی منتقل نشوند. کاربران در مقصد وارد شوند و اتصال ChatGPT را دوباره تأیید کنند.
7. TOTP رمزنگاری‌شده به کلید Auth مبدا وابسته است. بدون روش رسمی بازرمزنگاری و سازگاری کلیدها، مدیر در مقصد Enrollment بومی تازه انجام دهد؛ تا MFA معتبر، کد OAuth صادر نمی‌شود.

## پذیرش و تغییر اتصال سایت

قبل از Cutover، ورود و تغییر رمز، Enrollment و MFA مدیر، دسترسی دانش‌آموز به دادهٔ خودش، تخصیص فعلی دبیر، Consent، PKCE، Refresh، Disconnect و سرویس آزمون قبلی بررسی شوند. Callback واقعی ChatGPT را خود GPT Builder تولید می‌کند؛ Client از رابط مدیر با MFA ثبت می‌شود.

تغییر `config.js`، Merge و انتشار Pages فقط پس از آماده‌شدن حساب‌ها و داده‌های مدرسه انجام شود. برای بازگشت، تنظیم عمومی سایت به مبدا معتبر قبلی برگردد؛ حفظ مبدا و Backup امکان بازگشت را فراهم می‌کند. حذف داده یا منابع مشترک مقصد، روش rollback نصب مدرسه نیست.

مدیریت پروژه از `api.supabase.com` انجام می‌شود؛ برای بررسی سرویس مستقر نیز دامنهٔ `pukanizbahswrupscfmg.supabase.co` باید در فهرست شبکهٔ محیط باشد. دسترسی مستقیم به این دامنه در بررسی فعلی موفق است. برای بازسازی محیط، تنظیمات ذخیره‌شده باید Save و Publish شوند؛ ذخیرهٔ Draft به‌تنهایی اعمال شبکه یا انتشار محیط نیست.
